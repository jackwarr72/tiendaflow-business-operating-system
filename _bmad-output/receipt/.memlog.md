- (decision) AD-1 paradigm: server-first layered, same as parent. Receipt HTML is rendered server-side by a route handler from the typed Receipt object; client components are leaves receiving props only.
- (decision) AD-2 folio: reuse order.id as ORD-<id>. No migration, no new column. Binds all receipt consumers. Prevents a folio counter that can diverge from the order record.
- (decision) AD-3 format: print-to-PDF via server-rendered standalone HTML returned with Content-Disposition attachment. No puppeteer/playwright. Binds all export. Prevents a headless-browser dependency for a fidelity requirement that does not exist yet.
- (assumption) ASSUMPTION: no IVA/tax line. Schema has no tax rate, no business RFC, no tax category. Adding one is a schema+migration change deferred to a tax requirement.
- (assumption) ASSUMPTION: business name = stores.name, phone/email not yet modeled on stores. Receipt header uses store name; contact lines render only when fields exist.
- (assumption) ASSUMPTION: quick-sale hardcodes status=completed/paymentStatus=paid, so the receipt is only offered for paid orders; the route itself is the guard, not the UI.
- (direction) Trigger points (user-confirmed default): button on /ventas order card, button on quick-sale success screen, dedicated /recibo/<id> route reachable by link.
- (decision) AD-4 money: single src/lib/money.ts formats MXN with 2 decimals. Receipt HTML and any future CSV/PDF consume the same helper; no inline toLocaleString in receipt code. Prevents UI/export currency drift.
- (decision) AD-5 receipt data contract: Receipt object defined once in src/app/recibo/types.ts (folio, store, customer, items[], totals, payment). HTML exporter consumes it as-is, never re-derives columns from raw rows.
- (decision) AD-6 single generation entry point: getReceipt(orderId) in src/app/recibo/actions.ts is the only query; UI and route both call it. Unknown/foreign order -> null, never a thrown error.
- (decision) AD-7 store scoping: getReceipt filters orders by storeId (via getStoreId). A receipt link valid in one store returns 404 in another; no cross-store receipt leakage.
- (decision) AD-8 paid-only guard: the route is the guard. Non-paid paymentStatus or cancelled status -> 404, never a 500/stack trace. UI buttons are hints, not authorization.
- (decision) AD-9 receipt set closed: one kind only - order receipt. A new kind = enum value + query in actions.ts + a row in the set table. No bespoke receipt outside this set.
- (decision) AD-10 standalone HTML: receipt HTML is self-contained (inline CSS, no external requests, no JS). Renders correctly when printed and when opened offline.
- (decision) AD-11 client leaves: receipt button components are client leaves receiving an order id prop; they never fetch. No client-side receipt rendering.
- (decision) AD-12 link surface: /recibo/<id> is the canonical shareable receipt URL. Every trigger point links to it; the route does the work, UI only links.
